# Phase 6 — Production-hardening foundation

This delivery prepares and tests application controls; it is not authorization to deploy or a claim of completed production certification.

## Financial concurrency preservation

Existing user/quote/order/payout row locking and unique constraints remain. Quote consumption and order insertion are transactional; accepted terms cannot be edited. Chain event identities and journal event keys provide permanent idempotency. Payout requests retain stable provider keys and definitive-failure retry rules. Referral rewards additionally lock both users in sorted order, lock the referral and use one permanent journal event key. No broad retries were added to financial provider calls.

PostgreSQL transactions now use lock, statement and idle-in-transaction timeouts. Errors roll back and remain sanitized. Supporting migration 006 is additive; prior migration hashes are unchanged. Referral exposure after a qualifying payout reversal is reviewed, not silently rewritten.

## Workers and Redis

Blockchain, payout and engagement workers use shared validated Redis settings: required explicit URL, TLS when rediss, bounded connection timeout, exponential/capped reconnect delay and correct BullMQ retry semantics. Production startup requires Redis; there is no in-memory production queue or lock fallback. Existing queues remain isolated (`dt-blockchain`, `dt-payouts`, `dt-engagement`).

BullMQ retries/backoff, stable/deduplicated IDs, persisted failed jobs, database worker_failures, leases and graceful close are present. PostgreSQL supplies durable work recovery; Redis acknowledgement alone does not grant financial authority. Engagement dispatch batches are bounded at 100. Referral checks rotate by last checked time. Production Redis must use persistence and a no-eviction policy; HA, failover, restore and worker-kill drills require live infrastructure.

## Resilience and observability

External notification calls use an abort-aware timeout/circuit primitive. Provider ports require stable idempotency keys; an adapter must respect cancellation and reconcile ambiguous acceptance. Never wrap a non-idempotent bank transfer in this retry utility.

API request IDs are generated by the server and returned in headers/errors. Structured request logs include method, status, duration and request ID. Existing financial/worker logs include safe order/payout/job references. Raw secrets, passwords, OTP values, recipient addresses, bank numbers and provider exceptions are not logged by the new code.

ObservabilityService is a provider-neutral bounded-cardinality sink for timings/errors. API/provider latency and engagement queue metrics are recorded. Admin health summarizes worker heartbeats, queue statuses, dead letters and support backlog. Seven-day diagnostic samples are pruned by the engagement worker; this is operational telemetry retention, not financial record retention. Additional production export/alert thresholds for chain lag and payout age should be configured against existing timestamps and monitored in staging.

Public liveness/readiness do not expose configuration secrets. Readiness checks database migration 006, Redis/queue accessibility when configured, and fresh worker heartbeats when required. Worker activity is not proof of vendor solvency/connectivity or successful money movement; direct vendor acceptance remains a deployment gate.

## Security boundaries

Separate support, referral, notification and system-monitor permissions; all sensitive admin mutations require a reason and audit record. No new account receives these roles automatically. Token registrations and support messages are encrypted. Recipient data is only decrypted for a configured provider call. Mandatory security alerts cannot be fully disabled. PIN hashing, attempt lockout, current-password checks and session revocation remain server-side.

Account deletion deactivates an eligible empty account and retains financial/audit history. Legal text, anonymization rules and retention approvals must be supplied by the operator. Mock object storage never exposes a public private-file URL or marks bytes uploaded.

## Real-infrastructure harness

The normal suite uses PostgreSQL-compatible PGlite, not multi-connection PostgreSQL. Run the exact Phase 6 Nest/API suite with a dedicated database named `dt_phase6_test` (or `dt_phase6_test_<suffix>`):

```sh
npm run build --workspace @dt/backend
PHASE6_POSTGRES_URL='postgresql://test-user:REPLACE@localhost/dt_phase6_test' node --test backend/test/phase6.test.mjs
PHASE6_REDIS_URL='redis://localhost:6379/15' node --test backend/test/redis-integration.mjs
```

The PostgreSQL harness creates one random private schema, runs real transactions on a 12-connection pool, and removes only that schema afterwards. Never use production credentials. Concurrent tests cover quote/order consumption, duplicate deposit/ledger processing, payout creation and referral credit. Redis test uses a random isolated queue, tests retry/deduplication, and cleans up that queue. The Redis test is explicitly skipped without its test URL. No successful live PostgreSQL/Redis validation is claimed in this environment.

## Remaining deployment gates

- Real PostgreSQL/Redis concurrency, failover, outbox recovery and load/soak execution.
- Audited notification vendor adapters, native push consent/token lifecycle and delivery receipts.
- Private object storage, byte validation/malware inspection and expiry.
- Native Android/iOS builds, secure-device/biometric/2FA enrollment testing.
- Published privacy/terms and approved retention handling.
- Browser acceptance for the Next.js admin and real provider credential acceptance.

Phase 7 and production deployment remain unstarted.
